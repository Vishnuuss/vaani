# Run 853: three defects, and the one that mattered most

**10 September 2026 · Project Vaani · MB Solar Hub (workflow 2)**

An 85-second call that captured all six qualification fields and still contained
three defects the client would notice. Each is fixed, tested and deployed. The
third had been silently corrupting every lead record this project has produced.

---

## 1. The company name was spelled out letter by letter

The first words every caller heard were stored like this:

    Namaskaram andi, MB Solar Hub nunchi Priya matladutunnanu.

That is Telugu written in Latin letters. The TTS runs `language: te`, so it does
not read Latin as English — it reads it as characters, and the caller hears the
company name spelled out. Every other line in the call was in Telugu script and
sounded correct. Only the greeting was wrong, and the greeting is the one line
that decides whether the caller stays on the phone.

**Fixed:** the greeting is now Telugu script, verified by read-back.

**And the class is closed.** Fixing the string fixes one call; the CLASS is
"Latin-script Telugu reaches a Telugu TTS", and it can return through the
dashboard, a migration, or anyone typing a greeting the way it is easiest to
type. Nothing would notice — no error, no failing test, a transcript that looks
fine. So `tools/set_greeting.py` refuses at the write.

It does **not** ban Latin. Telugu callers code-switch constantly and this project
has a standing rule against forcing language purity. A sentence with English
words in it is correct; a sentence with **no** Telugu script in it is
transliteration, and only that is refused. Bare capitals ("MB") are warned about
separately, because two letters with no vowel are read as two letters.

## 2. He was asked the question he had just answered

    bot : which area or city do you live in?
    user: Anandpur.
    bot : good, Anandpur. which city or region do you live in?
    user: why are you asking again?

It repeated his answer back **and** asked for it again in the same sentence. The
same call asked his name twice and the site survey three times, so this was never
about locations.

Two mechanisms had to fail together, and both did.

**`extractor.py` is async by design.** It sits off the critical path because that
is worth ~0.3 s a turn, so its verdict lands a turn late. Until it does, `known`
has no `location`, `still_need` still lists it, and the state block is the last
and most authoritative thing the model reads. **It asked again because we told it
to.**

**The repeat guard could never have caught it,** and this half generalises:
`_is_repeat` compares the WORDS of two replies. The two questions were worded
differently — "ఏ ఏరియా లేదా సిటీలో" against "ఏ నగరం లేదా ప్రాంతంలో" — so it saw
two different strings. **A guard on wording cannot catch a repeat of subject.**

**Fixed:** `state.note_answer_to_last_ask` runs on the user turn, *before* the
reply is built. If we spoke a question about a field and the caller then said
something substantive, that field leaves `STILL_NEED` for one turn. If the
extractor confirms it, it moves to `known` and never returns. If it finds nothing
— he dodged, or STT garbled it — the field returns next turn and
`MAX_ASKS_PER_FIELD` still bounds it, so a dodged question is asked once more and
no more.

Two judgements, both found by a test rather than by reasoning:

- **`strip_fillers` is deliberately not reused here.** It returns the original
  when stripping would empty it, because a bare "um" is a real answer to "is
  anyone there?" and an empty name is worse than a wrong one (run 314). Right for
  storing a value, wrong for asking "was that an answer at all".
- **"సరే" is not treated as a backchannel.** It is the word "okay", and to *"shall
  we book a free site survey?"* it **is** the answer. Ruling it out would re-ask a
  man the question he just said yes to — the exact defect being fixed. Misreading
  an acknowledgement as an answer to an open field costs one turn; misreading a
  yes as noise costs the booking.

## 3. The lead record was never guarded at all

The record says `monthly_bill: 15`.

Fifteen rupees is not a monthly electricity bill. What makes it worse than merely
wrong: **a null is visibly missing and someone follows it up, while 15 looks like
an answer and nobody ever looks again.**

Everything built to catch it worked correctly. The caller's bill reached Sarvam
as "పది ఐదు గుంధల అండి" — a garbled "పదిహేను వేలు", fifteen thousand.
`amounts.parse_amount` returned `None` rather than guess.
`extractor._is_plausible_money` would have dropped 15 on sight.

And the record still says 15, because **there are two extraction paths and only
one was ever guarded**:

| path | guards |
|---|---|
| `vaani/extractor.py` | drops an implausible bill (run 295), strips "um" from a name (run 314), refuses a negative fact from the absence of a yes (run 312) |
| `pipecat_engine._do_extraction` | `self._gathered_context.update(extracted_data)` — raw model output, **no validation of any kind** |

The second path is the one that writes **the lead record and the client's webhook
payload**.

So every guard this project has built over weeks protected the *conversation*,
while the artefact the business is actually paid for took whatever the model
said.

**Fixed:** `vaani/lead_record.sanitise` now runs before that update. It reuses
`amounts`, `completeness` and `_is_money_field` rather than restating any rule —
a second copy of "what is a plausible bill" is a second thing to drift, which is
the failure being fixed. It only ever **subtracts**: it drops what the existing
rules can prove is wrong, never invents, never rewrites a plausible figure, never
turns a null into a value. Control signals pass through untouched, and every drop
is logged so it is never silent.

## A defect that was not one

The transcript appeared to show the agent speaking in fragments — `"సరే,"` then
`"మీ"` then the full sentence — which reads exactly like being cut off mid-word.

It was not. Run 853's event log contains **zero** interruption events. Those lines
are cumulative *streaming* chunks logged as the reply generates; the third
contains the second. Recorded here because the transcript view will keep looking
like truncation, and the next person to read it will reach for the barge-in gate
for no reason.

## Voice clarity

The configured voice was a **private clone**, and measured at real 8 kHz
telephony against the nine stock Telugu voices on identical text it was the worst
option available: the fastest talker of all six candidates, with every stock voice
14–38% slower on the same words. Rushed speech on a narrowband line is precisely
what "not clear" sounds like.

Two other measurements worth keeping:

- **Sarika — Calm Spirit** is effectively unusable: RMS 0.017 against ~0.15 for
  the rest, 71% near-silence. It would be inaudible on a phone.
- **Sindhu — Conversational Partner**, despite the name, has the weakest
  consonant definition of the set (HF ratio 0.053 against ~0.13), which is the
  worst trait to carry onto an 8 kHz line.

**Changed to Shanti — Calm Authority**: strongest level (RMS 0.175), good
consonant definition, 26% slower than the clone, matching the persona brief of
calm, respectful and confident.

## Latency, unresolved

Run 853 measured p50 1.055 s server-side against a 800 ms budget, of which the
LLM was 0.561 s on average. `reasoning_effort: low` is already applied and is
already worth a great deal — measured TTFT p50 631 ms with it against 1,699 ms
without. Reaching the sub-500 ms target therefore requires a **non-reasoning
model**, which is a quality trade on Telugu and a decision to be made against
measurements, not assumed.
