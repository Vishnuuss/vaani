# 35 — Phase 0 audit: what is actually broken

**11 September 2026**

The client asked for a full architecture — transcript event manager, normalization layer,
understanding stage, conversation state, response policy, validator — to be designed and built.

This audit was run first, as the brief itself instructed. Its main finding is that **most of
that architecture already exists in this codebase**, and the observed failures are not caused
by its absence. They are caused by four specific, located defects, three of which are a single
constant or a single sentence.

Nothing has been changed. This is an audit.

---

## The evidence base

All 8 real phone calls placed on 11 September, pulled from the live Vaani server
(`tools/vaani_runs.py`), with per-turn latency decomposition and full transcripts.

| Workflow | Runs | Agent |
|---|---|---|
| 2 | 871, 867, 866, 865, 864 | MB Solar |

| 4 | 870 | Tata Solar |
| 6 | 868 | BS Wealth plot/investing |

**69 measured turns.** Two of the eight calls (864, 870) ended in `user_hangup` with the caller
audibly angry.

## B. Failure points — the four defects, each traced to code

### B1. The Telugu turn detector is NOT RUNNING. All four agents use a fixed 0.6s timer.

Measured today: **0 of 69 turns had an endpoint under 0.6s.** Not one, across four different
agents. That is the signature of a floor, not a distribution.

The stored workflow configuration was read back from the live server for all four agents. Every
one of them is set to:

```
turn_stop_strategy: "transcription"
```

In `_build_user_turn_stop_strategies` (`turn_taking.py:188-344`) the entire Telugu turn-detection
stack lives inside `if strategy == "turn_analyzer":`. Anything else falls through to the last
line of the function:

```python
turn_taking.py:344        return [SpeechTimeoutUserTurnStopStrategy()]
```

That is pipecat's fixed timer, constructed **with no arguments**, so it takes its own defaults
(`speech_timeout_user_turn_stop_strategy.py:50-54`): `user_speech_timeout = 0.6` and
`wait_for_transcript = True`. Add Silero's `stop_secs = 0.2` and the floor is:

**0.20 + 0.60 = 0.80s, on every turn, before the LLM is asked anything.**

Measured minimum endpoint today, by workflow: 0.831 / 0.838 / 0.847 / 0.854 / 0.941 / 0.954s.
The code already names this exact number — `turn_taking.py:194-196` calls it "a dead-constant
0.80s endpoint on runs 110 and 163".

**The consequences are larger than the latency:**

- `TeluguTurnAnalyzer`, the prosody model trained on this agent's own caller recordings, is not
  on the call path.
- Neither is the `audio-native` Whisper-encoder model. Workflow 2 has `turn_model:
  "audio-native"` stored — **dead config**, read only inside the branch that never executes.
- So is workflow 2's carefully tuned `endpoint_min_secs: 0.3`, `endpoint_max_secs: 2.2`,
  `endpoint_unsure_floor_secs: 0.9`. **All dead.** Someone already lowered the endpoint floor to
  0.3s for MB Solar and it changed nothing, because the code that reads it never runs.
- `semantic_turn_completion: true` is stored on all four agents. It is checked at
  `turn_taking.py:300`, also inside the dead branch. **Also dead.**

This reframes the whole latency question. The answer is not to tune the detector's timers — it
is that **the detector is switched off**, and the weeks of work measuring and retraining it
(docs 29-33) have been measuring something that does not run on these calls.

Whether to switch it back on is a real decision, not a formality: `turn_stop_strategy` was moved
to `"transcription"` deliberately, during the detector comparison on 10 Sep
(`turn_taking.py:171-175`), and the filler guard was then written to compensate for what that
switch broke. Turning it on changes turn-taking behaviour on a live client agent. But it should
be an informed choice, and right now it is not being made at all.

### B2. The ask budget is charged to the wrong field, so it never binds

`MAX_ASKS_PER_FIELD = 2` (`state.py:202`) exists and is correct. Yet today:

- run 866 asked about the rooftop **three** times — "చెప్పాను కదా ఎన్ని సార్లు చెప్పాలి"
  (*I told you, how many times must I say it*)
- run 870 asked own-vs-rent **four** times — "నేను ఎన్నిసార్లు చెప్పాలి?", then
  "చెత్త చెత్త మాట్లాడొద్దు కదా" (*stop talking rubbish*) — **hung up**
- run 864 asked his name after he had given it — **hung up**

`commit_ask()` (`state.py:433`) charges `pending_ask` — *the field the state block nominated* —
not the field the model actually asked about. The codebase already documents that these diverge
(`state.py:966-971`: "the state correctly nominated monthly_bill and the model asked about
location instead"). When they diverge, the budget is spent on the wrong field and the field
actually being repeated is never bounded.

Two fixes for repetition already shipped **before** today's calls — `22477bb` (10 Sep,
`answered_pending`) and `b75f720` (11 Sep 10:32, the repeat guard that "was dead on every call").
Today's calls ran 10:45–14:09 IST, after both. They still repeat. Either the latest was not
deployed in time, or — more likely — neither addresses this path: `_is_repeat` compares *words*,
and run 870's four asks were each worded differently. **A guard on wording cannot catch a repeat
of subject.** That sentence is from the project's own commit message, and it is still true.

### B3. "That cannot be your bill" is written in code — and it throws the lead's data away

Runs 864 and 868: the caller states 50–60 lakhs, and the agent effectively calls them a liar.
This is not model invention. It is a deterministic gate:

1. `amounts.py:138` — `MAX_PLAUSIBLE = 5_000_000` (₹50 lakh/month).
2. `parse_amount` reads "50 to 60 lakhs" **correctly** (lo 50L, hi 60L) but the range branch
   (`:320-325`) returns the **midpoint, 55 lakh** — 10% over the cap.
3. `state.py:247-254` — `if not amount.plausible: self.doubted = amount; return False`.
   **The figure is not stored.**
4. `state.py:1026-1031` writes into the state block: *"THEY SAID THEIR BILL IS {said} — that
   cannot be a monthly electricity bill. Say warmly that it sounds much larger than usual and
   ask them to confirm the monthly figure."*
5. `alternatives()` returns `[]` for a range (`amounts.py:189`), so the gentle
   "thousands or lakhs?" repair the design intended is unavailable — it falls back to the blunt
   challenge.
6. Downstream the value is nulled out of the lead record (`pipecat_engine.py:1103-1117`).

So a commercial/factory lead — the *most valuable* kind for a solar business — is contradicted
and then has their number deleted. Three of today's five MB Solar callers were factory or
commercial and quoted 50–80 lakhs.

One caveat that must be checked before changing the threshold: run 871 stored `monthly_bill:
70000` from a spoken "70,000", so both readings genuinely occur on this line. Whether today's
"70 lakhs" callers meant lakhs, or were mis-heard thousands, is **not established** and should
not be assumed in either direction.

### B4. Bookish Telugu: the instruction to reword is in the code, in three places

Doc 34 measured that the first ask is near-verbatim to the hand-written question and every
re-ask drifts toward written Telugu, but could not find what caused the drift. It is here:

| Site | Text |
|---|---|
| `state.py:972-979` (state block — the **last** thing the model reads) | "The WORDING is yours… **if you have asked before, ask it a DIFFERENT way**." |
| `layers/01_persona/te-IN.md:143-146` | "Never say the same sentence twice… say it a different, shorter way" |
| `coach.py:112-117` (`confused` cue, weight 94) | "Ask it again a shorter way" |

The model is *told* to invent new wording on a re-ask, and invented Telugu defaults to the
written register.

This was a deliberate change on 7 Sep, away from "IN THESE EXACT WORDS … do not reword it",
because verbatim repetition produced run 817's complaint that the agent "is 100% scripted". So
there is a genuine tension, and it should be named rather than papered over:

> exact wording → robotic recitation · free wording → bookish drift

Doc 34's proposal — two or three **pre-written** spoken variants per question — is the only
option on the table that resolves both, and it must **replace** the free-rephrase clause, not sit
beside it.

Compounding this: `speech_register.py` corrects register post-generation, but only for ~55
**nouns**; it deliberately excludes verb morphology (`:35-42`). Every bookish form doc 34
complained about (నివసిస్తున్నారు, చేయించుకోవాలనుకుంటున్నారా) is a **verb**. Nothing corrects them.

## C. The one-turn trace

Caller says: *"Naaku 59 lakshala budget undi, Vijayawada lo 2BHK kavali. Parking unda?"*

| # | Stage | Where | What happens now | Latency | Failure mode |
|---|---|---|---|---|---|
| 1 | VAD | `run_pipeline.py:1021` | Silero, `stop_secs=0.2` | 0.20s | any noise resets the clock |
| 2 | Turn end | `turn_taking.py:344` | **pipecat fixed 0.6s timer**, also waits for a transcript | **≥0.60s** | **floor B1** — the Telugu detector is configured but never reached |
| 3 | STT final | `sarvam_realtime_stt.py:252` | Sarvam websocket | ~0.35-0.45s measured | socket flap ⇒ every turn "blind" ⇒ fast path shut |

| 5 | Normalization | `amounts.py:262-328` | "59 lakhs" → 5,900,000 ✓ | ~0 | ranges collapse to a midpoint → **B3** |
| 6 | Understanding | `extractor.py` | **ASYNC — lands one turn late, by design** | off path | field not in `known` yet ⇒ still in `STILL_NEED` ⇒ **re-ask** |
| 7 | State | `state.py` `render()` | builds STILL_NEED, nominates `pending_ask` | ~0 | nominated ≠ asked ⇒ **B2** |
| 8 | Policy | state block text | priority is implicit in prose, not code | — | "answer their question first" is a *request*, not enforced |

The customer's actual question ("parking unda?") has no dedicated path. Whether it gets answered
depends on the model obeying prose in the state block.

## D. What is missing (and only this)

| Brief part | Status |
|---|---|
| 6 raw transcript preserved · 7 normalization · 9 state · 10 update rules · 13 question memory · 16 validator | **already built** |
| 5 transcript event manager / turn_id | **missing** — no id on any in-flight LLM or TTS work |
| 18 barge-in safety | **missing** — `barge_in.py` cancels nothing; the gate is OFF by default, so every one-word interim transcript interrupts; `ReplyFilter` never handles `InterruptionFrame`, and the 24-char holdback plus `_pending_repeat` flush on `LLMFullResponseEndFrame` with no check that an interruption happened between. **Text generated before a barge-in can still be spoken.** This is the shape of run 865. |
| 25 per-turn structured logging | **missing** — nothing records *why* an endpoint took as long as it did |

`ReplyFilter._stale` (`brain_processor.py:529`) is the closest existing guard, but it is a
**start-time** snapshot: a generation that began while the caller was silent and only later
became obsolete is never marked stale.

## E. Minimal change plan — in this order

| # | Change | Files | Risk |
|---|---|---|---|
| 1 | Instrument the endpoint stage: emit which `_wait_secs` branch ran, the computed wait, the probability, and the VAD/analyzer/STT split | `telugu_turn.py`, `run_pipeline.py` | none — logging only |
| 2 | Charge `commit_ask` to the field actually asked, not the one nominated | `state.py`, `brain_processor.py` | medium — has a test suite already |
| 3 | Replace the free-rephrase clause with doc 34's pre-written variants | `state.py:979`, `te-IN.md`, `coach.py` | low — prompt text |
| 4 | Widen the range branch: keep `low`/`high` instead of a midpoint; raise or context-gate `MAX_PLAUSIBLE` for commercial property | `amounts.py`, `state.py:1008-1031` | low, but **decide the lakhs-vs-thousands question first** |
| 5 | Decide whether the Telugu turn detector goes back on the call path (`turn_stop_strategy`) — a stored-config flip, no deploy, reversible in seconds | stored workflow config | **behavioural** — test on one agent, one call, first |
| 6 | Add turn_id; reject stale generations; drop buffered text on interruption | `brain_processor.py` | **highest** — leave until last |

Changes 1–4 do not touch the turn detector at all. Change 5 is a stored-config edit, which
per this project's own history overrides every code default — and is reversible in seconds.

## F. Latency risk

| Proposal | Effect |
|---|---|
| Put the Telugu detector back on the path (`turn_stop_strategy: turn_analyzer`) | Its whole purpose is to end a turn *early* when it is confident, and never later than the timer. Measured on 30 recordings (`turn_taking.py:226-231`): audio-native 16.0% cut-off @ 0.76s wait vs prosody 23.0% @ 0.48s. Potentially **−0.2s/turn with fewer cut-offs** — but this is a behaviour change on a live agent and must be one agent, one call at a time. |
| Fix the ask budget | none — pure bookkeeping |
| Pre-written variants | none — replaces text of the same length |
| Range/plausibility fix | none |
| turn_id + stale rejection | negligible if it is a comparison; a *wait* would cost a turn |
| Making `extractor` synchronous | **+0.3s/turn — do not do this.** The async design is deliberate and correct; fix the ask budget instead. |
| A second "understanding" LLM call (brief Part 20) | **+0.3-0.7s/turn.** Not justified: the understanding stage already exists and is off the critical path. Recommend against. |

## G. Test plan

The stored workflow config **has now been read back** for all four agents, and it changed this
document's main finding — see B1. What it holds:

| Key | wf2 (MB Solar) | wf3 / wf4 / wf6 |
|---|---|---|
| `turn_stop_strategy` | `transcription` | `transcription` |
| `turn_model` | `audio-native` *(dead)* | unset *(dead)* |
| `endpoint_min/max_secs` | 0.3 / 2.2 *(dead)* | unset *(dead)* |
| `endpoint_unsure_floor_secs` | 0.9 *(dead)* | unset *(dead)* |
| `semantic_turn_completion` | true *(dead)* | true *(dead)* |
| `llm_hedge` | 2 | 3 |
| `barge_in_gate_enabled` | true | not set in the keys read |
| `filler_turn_guard_enabled` | true | true |
| `max_call_duration` | 200s | — |

Every key marked *(dead)* is read only inside the `turn_analyzer` branch that these agents never
enter. This is the second time this project has been bitten by exactly this: `turn_taking.py:191-196`
documents an earlier instance where a `.get()` default was never reached and "every call fell
through to the fixed 0.6s speech timeout".

**A standing lesson for this codebase: a stored config value is not a running config value.**
Anything changed here must be verified by measurement on a real call, not by reading it back.

Then, per change, in this order: existing suite (161 tests across 14 suites) → text-chat probe
(`tools/vaani_probe.py`, free, hits the deployed code) → **one** real call → read the transcript
and the latency table → only then the next change.

The regression cases worth adding are today's own failures, which are better than invented ones:
a field answered then re-asked (866), a reworded re-ask ×4 (870), a range bill (864/868), a
customer question mid-qualification (871).

## Two claims NOT made here

- **Nothing has been changed.** No code, no prompt, no config.
- **The 8–14 second stalls are not explained.** Runs 871 (13.7s), 868 (10.8s) and 865 (8.8s) have
  candidate causes — the 5.0s `USER_TURN_STOP_TIMEOUT` backstop, a flapping STT socket (the fixed
  timer also **waits for a transcript**, so no transcript means no turn end), or the filler guard
  deferring up to 2×1.2s (it is enabled on all four agents) — but **nothing logs which one
  fired**, so attributing them now would be a guess. That is the first reason to do the
  instrumentation change before any other. Note the earlier suspicion that the audio-native
  Whisper encoder was blocking the frame loop is now **ruled out**: it is not running.

- **This audit was wrong once already, and was corrected by measurement.** Its first version
  attributed the 0.85s floor to `_wait_secs` and the `endpoint_min_secs = 0.70` code default.
  Reading the live stored config disproved that: those values are overridden *and* dead. The
  finding survived, the mechanism did not. Treat every remaining "candidate cause" here the same
  way until it is measured.
